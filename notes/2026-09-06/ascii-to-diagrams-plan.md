# ASCII to real diagrams — design, reasoning, and orchestration plan

Date: 2026-09-06
Status: scope approved, execution pending
Verification model: evidence gates, not agent self-reports

## Context

The 46 published treatises draw their figures as ASCII art inside fenced code
blocks. Rendered, they are grey monospace boxes. For a think tank whose entire
proposition is engineering rigour, a hand-drawn `+---+` where an architecture
diagram belongs reads as unfinished work.

Corpus-wide there are 181 such blocks across 23 files. Scope was deliberately cut
to the **7 papers a buyer actually opens** (underwriting, CyHAZOP, ATQ, FMECA,
liquid cooling, frontier hardware). The 66 blocks in the Cascading Failure paper
are excluded on purpose: that document still carries 351 unfilled
`[investment required]` placeholders, so restyling its figures would be polishing
the wrong thing.

## Already done (phase 1)

13 of 39 blocks converted with no new dependency:

- 10 boxed banner captions became `####` headings. Each already sat directly above
  a real markdown table, so they were captions drawn in ASCII, not figures.
- The ATQ Boltzmann trajectory comparison became a 7-column table. It was also
  duplicated byte-for-byte in the compiler source; the table replaced both copies.
- The Frontier 4-BOM architecture matrix became a 4-row table.

One phase-1 item remains: **ATQ "Interactive Card Terminal Architecture"** (11

ordered list. It is not a diagram and must not be made into one.

## Decision: how diagrams get rendered

**A. Mermaid bundled eagerly.** Rejected. Mermaid is several hundred KB. The
previous commit removed ~900 KB of needless payload from every route; spending it
straight back on pages that mostly have no diagram is a regression by another name.

**B. Mermaid, lazily imported only when a block exists. CHOSEN.** `MarkdownViewer`
detects a mermaid fence and dynamic-imports the library only then. Routes without a
diagram pay nothing; the cost lands after hydration on the few paper pages that
actually have figures.

**C. Build-time SVG via `@mermaid-js/mermaid-cli`.** Best runtime cost, but drags
Puppeteer and a headless Chromium into the Railway Docker build. That is a large,
fragile dependency for a build that currently needs nothing but Node.

**D. Hand-built inline SVG matching `theory-diagrams/`.** Highest quality and
already the site's visual language, but 26 bespoke components is disproportionate,
and the figures would live in TSX while the prose lives in markdown.

Why B is safe to choose now: the markdown stores Mermaid *source* either way. If
the bundle cost later proves unacceptable, moving to option C is a build-step
change with **no edit to any treatise**. The decision is reversible, which is the
main reason to prefer it.

## Constraints that govern every change

1. **Edit the compiler, never the markdown.** All 7 files are generated by a
   `compile_*.py`. A direct `.md` edit is silently reverted on the next run.
2. **Do not reintroduce the escaping bug.** Literals are now a mix of raw (`r"""`)
   and non-raw. In a raw literal write `\text`; in a non-raw literal write
   `\\text`. Getting this backwards produced 408 broken expressions earlier in
   this work, and the build did not catch it.
3. **Information preservation is the acceptance test.** Every label, number, unit
   and threshold in the ASCII must survive into the Mermaid. A diagram that looks
   better but drops `Delta E = 8.4 eV` is a failure, not an improvement.
4. **Tabular content stays tabular.** If a block is comparison data it becomes a
   markdown table, not a flowchart. Numbers read badly inside node boxes.
5. **Theme to the design tokens**: `#E05A10` accent, `#0B0C0E` ground, `#22252C`
   edges, mono labels, consistent with `web/src/components/theory-diagrams/`.

## How the Karpathy rules apply here

The repo's own execution rules govern this work; they are what the scope decisions
above are actually derived from.

- **Think before coding.** The four rendering options were compared and the
  trade-off stated before any dependency was added. Option B was chosen for
  reversibility, not preference.
- **Simplicity first.** No build-time SVG pipeline, no Puppeteer, no 26 bespoke
  TSX components. Lazy import plus markdown source is the smallest thing that
  works. The test suite is six focused tests, not a coverage target.
- **Surgical changes.** One agent, one compiler, no drive-by edits. The scope gate
  (`git diff --name-only`) is enforced per agent, and an agent that touches another
  file must revert and report it.
- **Goal-driven, loop until verified.** Every stage states a testable outcome and
  the exact command that proves it. "Looks fine" is not an accepted result, which
  is why stage 3 is adversarial and re-derives the facts from git rather than
  trusting the conversion agent's own summary.

Two failures earlier in this work are the reason the gates are shaped this way:
the build audit passed green while 1,346 LaTeX expressions were corrupt (it only
compares word counts), and a raw-string conversion silently doubled 408
backslashes. Both were caught only by rendering real pages and counting.

## Orchestration

One orchestrator, specialist subagents, evidence-based gates. The orchestrator
decomposes, assigns file ownership and verifies. It does not author diagrams.

- **Stage 1 (blocking): renderer.** One agent adds lazy Mermaid support and theming
  to `MarkdownViewer.tsx`. Everything downstream depends on it, so it is verified
  before any conversion begins.
- **Stage 2 (parallel): conversion.** Seven agents, one per compiler. Ownership is
  1:1 and disjoint, so two agents cannot touch the same file.
- **Stage 3 (parallel): adversarial QA.** A different agent per file re-derives the
  information content of the original ASCII from git history and diffs it against
  the Mermaid, hunting for dropped labels and values. It reports; it does not fix.
- **Stage 4: integration.** Full build, corpus-wide render sweep, scope audit.

## Gate 0 (overriding): NO CONTENT LOSS, EVER

This outranks every other gate. Treatises have been shortened and truncated in the
past, and the existing tooling cannot detect it.

**Why the current tooling is blind to it.** `audit-publications.js` compares word
counts between the markdown on disk and the generated JSON bundle. Both sit
*upstream of rendering*, so the comparison is structurally incapable of noticing
that a page rendered short. It reported "AUDIT PASSED: All 46 documents at 100%
content fidelity" on the same day one unbalanced code fence was swallowing ~90
lines of the ATQ treatise into a `<pre>`, killing 178 equations and 10 headings.
Green build, broken page, no signal.

**The fix: `web/scripts/audit-rendered-completeness.js`.** It compares SOURCE PROSE
against the VISIBLE TEXT of the actual rendered page, per document, and exits
non-zero when a line is missing.

Design decisions that make it trustworthy rather than merely reassuring:

- **A dead server is not a pass.** Any page under 5,000 bytes, or a non-200, is
  reported INCONCLUSIVE with exit code 2, never as clean. This matters: during this
  session a rebuilding dev server produced false "0 errors" readings three separate
  times, and once a false "100% content loss". An audit that cannot tell the
  difference between "fine" and "not measured" is worse than no audit.
- **It excludes only what the renderer legitimately restructures**: fenced code
  blocks, table rows (split into cells), the leading H1/H2 (deliberately relocated
  to the hero card by `suppressLeadingTitle`), and list markers that become bullets.
  Everything else must appear verbatim.
- **Prefix matching** on the first 55 normalized characters, so trailing inline
  markup cannot cause a false miss.

Known content-destroying mechanisms this must keep watch over:

| Mechanism | What it can do |
|---|---|
| Unbalanced code fence | swallows the rest of the document into a `<pre>` |
| `splitRunInHeading()` | rewrites author headings, demoting half the title into body text |
| `sanitizeMarkdownContent()` | strips leading content by regex; an over-broad pattern eats real prose |
| Unrecognised markdown | the hand-written parser has no fallback; unknown constructs degrade to plain paragraphs |
| ASCII to Mermaid conversion | the work in flight right now: a label or number dropped in translation |

**Rule for this project, permanently: a document may be reformatted, never
shortened.** If a conversion cannot preserve a fact, leave the block as it is and
report it. A slightly ugly block that is complete beats a beautiful one that lost
`Delta E = 8.4 eV`.

## Quality gates — a claim is not evidence

A conversion is accepted only when all of these pass:

| # | Gate | Command |
|---|---|---|
| 1 | Only the intended compiler changed | `git diff --name-only` |
| 2 | Content regenerates | `python3 scripts/<compiler>.py` |
| 3 | Build and fidelity audit pass | `npm run build` -> AUDIT PASSED 46/46 |
| 4 | Types clean | `npx tsc --noEmit` |
| 5 | No LaTeX regression | 0 control chars, 0 double-backslash-before-letter |
| 6 | No KaTeX regression | corpus sweep holds at 0 errors / 5,475 expressions |
| 7 | Diagrams actually render | mermaid nodes present, no parse errors |
| 8 | Information preserved | stage-3 QA finds no dropped label or value |
| **0** | **No prose lost, any document** | `node scripts/audit-rendered-completeness.js` -> AUDIT PASSED. Exit 2 (inconclusive) blocks just as hard as exit 1. |

Gate 6 exists because the earlier LaTeX repair proved the build audit only compares
word counts: it passed green while 1,346 expressions were corrupt. The rendered
sweep is the only gate that has ever caught that class of failure.

## Stage 5 (added 2026-09-06): a real test suite for the renderer

The gates above verify the *corpus*. They do not verify the *library*. "The agent
said mermaid works" is a claim. This project has already been burned once by a
green build hiding 1,346 corrupt expressions, so the library needs evidence too.

The repo currently has **no test framework** (no vitest, jest or playwright config,
no `test` script). Adding one is in scope here because it is the only way to
satisfy "all loaded and all requirements met".

Sequencing note: this stage runs AFTER the renderer agent finishes, because that
agent owns `web/package.json`. Two writers on one file is the failure mode the
whole file-ownership scheme exists to prevent.

Minimum useful suite, per Karpathy "simplicity first" - no speculative coverage:

1. **Dependency loads.** `mermaid` resolves, imports, and exposes `initialize`
   and `render`. Catches a missing or broken install directly.
2. **Version pinned.** The installed major matches what `package.json` declares,
   so a silent upgrade cannot change diagram syntax under us.
3. **Renders a diagram.** A minimal `flowchart` through the real library produces
   an `<svg>`. This is the actual requirement, not a mock of it.
4. **Parses every diagram we ship.** Extract all mermaid blocks from the 7 target
   papers and assert each one parses. This is the highest-value test: it fails the
   build if any author writes a node label mermaid rejects.
5. **No regression in the existing renderer.** `MarkdownViewer` still produces
   headings, tables and KaTeX for a fixture document. The mermaid branch must not
   disturb the other block types.
6. **Lazy-loading holds.** Assert mermaid is absent from the First Load JS of a
   route with no diagram. This is the constraint most likely to silently rot.

Wire as `npm test`, and run it in the same breath as `npm run build`.

## Rollback

Each stage is a separate commit. Reverting one conversion is a `git revert` of that
commit; the renderer and the other six files are unaffected. Nothing is pushed
until the full sweep is green.
